# 逐句教学循环（阶段二）

朴素版本的每一句代码都走一遍这个循环。一句代码 = 一次往返，不要合并。

## 一次循环的七步

1. **定位下一句要解决什么** — 用问题推进，不用代码推进：“现在我们有了列表，下一步要知道每个元素出现几次，缺什么？”
2. **补这一点语法** — 只讲这一句用到的那一个点：用法、一个两行的最小示例、一个常见坑。不列举同类 API，不讲更 Pythonic 的写法（那些留到收尾）。
3. **给出这一句代码** — 单独一行或一个 2~3 行的小块，能接在已有代码后面运行。
4. **标出语法来源** — 这一句里出现新元素时，逐个分类，详见下一节。
5. **解释这一句** — 说清它对数据做了什么变换，而不是复述语法名字。可以用一个具体输入说“这一行执行完，`counts` 变成 `{'a': 2}`”。
6. **让用户动手** — 每轮都要有，按用户状态选一种：
   - **选择题**：“`3` 后面第一个数字的下标是 A: 0 还是 B: 1？” 零基础阶段优先用这种，两三个选项，比开放提问好答。
   - **手推**：“先别跑，`i = 0`、`j = 2` 时 `nums[i] + nums[j] == target` 是 `True` 还是 `False`？”
   - **写**：“下一句请你写：把出现次数大于 1 的键收集起来。”
7. **对答案** — 用手工推演逐层展开验证，把中间值写出来：

   ```text
   nums[i] → nums[0] → 3
   nums[j] → nums[1] → 8
   3 + 8   → 11
   11 == 11 → True
   ```

   答对了就确认并推进；答错了先追问“你以为会是什么、为什么”，再指出偏差在哪一步。整句朴素解成型后再让用户在终端真跑一次。

## 语法来源标注

用户最容易卡的不是逻辑，是分不清“这个词是 Python 规定的，还是别人随手起的名字”。每出现新元素就分三类：

| 代码 | 类型 | 说明 |
|---|---|---|
| `for`、`in`、`if` | Python 关键字 | Python 规定，不能改 |
| `len`、`range`、`print` | 内置函数 | Python 提供，可以不用但名字固定 |
| `i`、`j`、`nums`、`counts` | 自定义命名 | 程序员自己起的，可以随便换 |

配套两个动作：

- 自定义名当场演示可替换：`for i in range(...)` 改成 `for banana in range(...)` 一样能跑，只要下面用到的地方一起改。
- 关键字别只说“不能改”，给一次反证：把 `for` 换成 `abc` 会直接报语法错误。

已经讲过的元素不用每轮重复列表，只标这一句里第一次出现的。用户开始自己主动说“`nums` 是自定义的吧”，就可以只在出现容易混的新词时再标。

## 颗粒度判断

- 用户连续两轮都答对且答得快 → 一次给一小块（比如整个 for 循环体），节奏放粗。
- 用户答错或沉默 → 拆得更细：先只写循环头，再写循环体第一行；开放提问改成选择题。
- 用户开始追问“为什么不用 X” → 记下来，放到阶段五处理，不要在这里展开。

## 反模式

- 一次性贴出完整函数再逐行注释 —— 这不是逐句教学。
- “你觉得下一步是什么？（答案是用字典计数，因为……）” —— 自问自答。
- 借“顺便说一下”把整个 `collections` 模块讲完。
- 思路方向错了，直接给正确答案和正确代码，跳过让他自己发现的机会。
- 反过来，语法硬错（`=` 写成 `==`、`print{i, j}`）还拐弯抹角让用户猜 —— 这类直接纠正。
- 只说 `for` 是 Python 语法，不说 `i`、`nums` 是可以随便改的自定义名字。
- 语法还没熟就催用户去终端跑，把报错变成新的困惑源。
- 在朴素版还没跑通时，先说“其实有更好的写法”。

## 收尾

朴素解跑通后，允许一次“写法润色”：把用户写的循环换成更地道的写法（`get` 默认值、`Counter`、解包），并说明这是可读性改写、不改变复杂度。润色不进入阶段三的性能讨论。
